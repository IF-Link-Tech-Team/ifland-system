# 🏆 黑客松现场系统 - 需求与数据结构合并文档 (PRD_and_Data.md)

## 1. 项目概述与定位

本项目是一个专为黑客松（Hackathon）线下活动设计的**"现场协同与展示系统"**。

**核心目标**：辅助已报名的现场选手进行线上快速组队、实时同步团队开发进度、接收赛事全局通知，并为现场大屏提供状态展示和倒计时功能。系统采用极简的移动端优先设计，并支持 PWA 离线 / 桌面安装。

---

## 2. 系统架构与基础设施规范

- **前端展示层**：Web 网页（需适配移动端为主，大屏端为辅）。
- **后端服务层**：需包含一个轻量级的"中转后端（Proxy Backend）"，负责持有 API 密钥并处理业务逻辑。**严禁前端直连数据库。**
- **底层数据库**：使用**飞书多维表格（Feishu Base）**。现场后台管理员将直接在飞书客户端内查阅、修改数据表，系统需实时响应飞书数据的变化。
- **默认头像**：未上传头像的用户，系统使用 [DiceBear API](https://api.dicebear.com) 生成专属默认头像（如 `https://api.dicebear.com/7.x/initials/svg?seed=111`）。用户可在 Dashboard 随时上传头像覆盖。

---

## 3. 系统路由规范

系统仅包含 **3 个纯粹路由**，全部遵循极简设计：

| 路由 | 鉴权 | 说明 |
|------|------|------|
| `/login` | ❌ 免鉴权 | 选手登录入口，输入 Builder 号即可进入系统 |
| `/dashboard` | ✅ 需鉴权 | 核心大厅，组队、接受邀请、修改队名等全部操作均在当前页以 Modal / Inline 方式完成，**不跳新页面** |
| `/screen` | ❌ 免鉴权 | 大屏端，纯公开只读页面，仅展示倒计时和全场队伍状态，**不可写** |

### 3.1 登录态方案（Phase 1 — Cookie 方案）

- **登录成功**：中转后端 `POST /api/auth/login` 校验 Builder 号成功后，在响应 Header 中设置 `Set-Cookie: auth_token={builderId}; Path=/; HttpOnly`。**同时 Response Body 必须返回完整的用户信息 `{ builderId, name, role, teamId }`**，以便前端一次性写入 React Context，避免登录后额外调用 `/api/user/me`。
- **后续请求**：前端所有 `/api/...` 请求自动携带该 Cookie。中转后端从 `Cookie` 中解析 `auth_token` 得到当前 `builderId`，作为当前操作用户身份。**绝不依赖前端在 Request Body 或 URL 参数中传递 builderId**，防止越权。
- **退出登录**：后端返回 `Set-Cookie: auth_token=; Path=/; HttpOnly; Max-Age=0` 清除 Cookie。
- **Phase 2 预留**：正式版切换为飞书 SSO 或 JWT Token 时，仅需修改 `/api/auth/login` 的实现逻辑和 Cookie 命名，前端业务逻辑 **0 改动**。

## 4. 用户角色定义

### 4.1 现场选手 (Hacker)

已通过报名审核的参赛者，拥有唯一身份凭证（Builder 号）。包含以下五种职业标签：

| 角色 | 英文名 | 方向 |
|------|--------|------|
| 引航者 | NAVIGATOR | 后端 / 算法 / AI |
| 编织者 | WEAVER | 前端 / 设计 / 交互 |
| 链接者 | LINKER | 产品 / 叙事 / 路演 |
| 造物者 | ARTIFICER | 硬件 / 嵌入式 / 3D 打印 |
| 破壁者 | ANOMALY | 其他非常规方向 |

### 4.2 后台管理员 (Admin)

不直接登录网页端系统，而是通过操作底层的**"飞书多维表格"**来实施全局控制（发布通知、解散团队、修改时间）。

## 5. 核心功能模块说明

### 5.1 登录鉴权模块

- **开发测试期策略**：提供"后门测试"，预设特定测试账号（如 Builder ID `111`, `222`, `333`）。输入测试账号直接进入系统，并拉取该账号在飞书表格中的预设信息。
- **正式版策略**："邮箱 + Builder 号"登录，具体交互待定，但底层校验逻辑均通过中转后端向飞书发起查询。

### 5.2 用户个人大厅 (Dashboard)

登录成功后的主界面。

- **个人名片展示**：显示选手头像（默认 DiceBear，支持上传覆盖）、Builder 号、姓名、**电话**、角色标签、自我介绍。
- **大屏传送门**：提供一个"小房子"图标按钮，点击后跳转至 `/screen` 全屏观看大屏实时内容。
- **PWA 安装入口**：
  - **安卓 / 鸿蒙**：点击直接触发系统级"添加到主屏幕"安装弹窗。
  - **iOS (Safari)**：点击后弹出一个 UI 引导图层（提示用户点击底部"分享"图标并选择"添加到主屏幕"），不可直接调用安装 API。

### 5.3 组队机制 (Team Formation) - 核心重点

采用**"绝对队长制 (Captain System)"**，杜绝并发冲突。

#### 双向确认制

组队采用**双向确认 + 严格锁位机制**：

1. **发起邀请**：处于"未组队"状态的选手 A，在界面输入选手 B 的 Builder 号并发送邀请。**后端自动创建一支新队伍**：`teamId` 采用"现有最大编号的数字后缀 + 1"规则（如现有 T-002，则新建 T-003），默认队名为"新建队伍"，将 A 设为 `captainId` 并加入 `memberIds`，同时将 B 的 Builder 号加入该队伍的 `pendingInvites`。A 的 `teamId` 更新为新队伍 ID。
2. **待处理邀请**：B 登录后，在 Dashboard 看到所有收到的邀请列表，可以"同意"或"忽略"。
3. **名额锁定**：判断队伍满员的标准是 `现有队员数 + 发出的未处理邀请数 >= 3`。一旦达到 3 人，队长的"发送邀请"按钮立即置灰禁用。
4. **排他与坑位释放**：当 B 点击"同意"加入甲队伍时，系统将 B 编入甲队伍，同时**全局遍历**其他所有队伍的受邀名单，将 B 从中剔除，使其他邀请自动失效，并释放其他队伍的坑位。
5. **队长确认**：A 自动成为该队**"队长"**。

#### 权限规则

- 仅队长拥有**发送邀请**权限。队员无法邀请他人。
- 仅队长可**修改队名**。
- 仅队长可**编写 / 修改队伍的一句话宣言**。
- 每队包含队长在内**最多 3 人**。

#### 团队展示

组队成功后，Dashboard 下方显示团队面板，以列状排列展示所有队员的名片信息（头像、姓名、身份、Builder 号），并展示队名和一句话宣言。

#### 离队与解散

- 选手点击**"申请离队"**按钮后，系统仅给该队员打上异常标记（供管理员后台处理），按钮文字瞬间变为**"已申请离队（等待管理员处理）"**并设为 Disabled，无需二次确认弹窗。
- 实际解散由后台管理员在飞书中操作（删除队伍记录或触发解散字段），前端侦测后将全队人员恢复至"未组队"状态。

### 5.4 状态与进度管理 (Status Management)

- **状态切换**：队长在 Dashboard 拥有三个状态切换按钮，可随时切换本队伍的当前进度：
  1. `头脑风暴中`
  2. `开发中`
  3. `Demo提交`

- **数据同步**：队长点击后，中转后端更新飞书表格。大屏页面轮询到变化后实时更新队伍状态展示。

### 5.5 全局控制与大屏展示 (Global Screen & Notifications)

- **大屏主界面** (`/screen`)：专为现场投屏设计的页面，包含两个核心元素：
  1. **全局倒计时**：读取飞书中配置的"比赛结束时间"，进行倒计时显示。
  2. **各小队状态看板**：按状态（头脑风暴 / 开发中 / 提交）分类或列表展示全场队伍的实时进度及队名 / 宣言。

- **双端紧急通知 (Red Banner & Marquee)**：
  - 当管理员在飞书表格填写"全局跑马灯通知"后。
  - **大屏端** (`/screen`)：顶部 / 底部出现滚动跑马灯横幅。
  - **手机端** (`/dashboard`)：所有在线选手的个人大厅页面顶部，出现醒目的小红条提示。

## 7. 技术实现与架构备注 (开发团队必读)

### 头像上传：敏捷开发与平滑过渡策略

#### 阶段一：Demo / 开发联调期（MVP 方案）

- **策略**：采用"本地服务器直存"**或直接调用飞书开放平台**"上传附件 API"。
- **要求**：将用户上传的图片直接保存在中转后端所在服务器的本地目录中（生成静态链接），或直接塞入飞书。
- **目的**：免去第三方云服务（OSS / CDN）的开通、域名绑定及跨域配置等繁琐工作，使团队 100% 聚焦于核心组队逻辑与数据流转的开发。
- **代码规范**：后端务必将文件上传逻辑封装为独立函数（如 `uploadAvatar()`），入参为图片流，出参为纯文本 URL。

#### 阶段二：正式上线期（生产方案）

- **策略**：无缝切换为"第三方云端对象存储（如阿里云 OSS、腾讯云 COS）"。
- **操作**：仅需修改 `uploadAvatar()` 函数内部逻辑，将图片推至云端并返回云端 URL，前端及数据库结构维持 **0 改动**。
- **数据迁移**：若需保留测试期数据，正式切换前，将本地测试头像批量上传至 OSS，并使用脚本 / 飞书批量替换功能更新表格中的 URL 前缀即可。

#### **当前处于开发联调期**，暂时不需要管阶段二。

## 8. 数据库设计原则与说明

- **数据源媒介**：系统底层数据库采用**飞书多维表格（Feishu Base）**。
- **数据流通架构（Demo 阶段适用）**：前端界面 ↔ 中转后端 (Proxy Server) ↔ 飞书开放平台 API。**禁止前端直接调用飞书 API。**
- **关联关系**：系统以 `Builder号` 作为用户的唯一标识主键，队伍与用户的双向绑定通过"单向关联字段"实现。
- **Mock 阶段数据结构**：采用**扁平化结构**，绝不深层嵌套（详见下方 `mock_data.json` 示例）。

## 9. 核心数据表设计

请现场管理团队 / 技术组在飞书多维表格中建立以下 **3 张**数据表，并严格对齐字段类型：

### 表 1：【用户表】 (User Table)

**用途：** 存储所有选手的个人基础信息及当前的组队归属状态。

| 字段名称 | 飞书字段类型 | 必填 | 备注 / 业务规则 |
|---|---|---|---|
| **Builder号** | 文本 (主键) | ✅ | 唯一身份标识（如 `111`, `A7X9`）。登录系统的唯一凭证。 |
| **姓名** | 文本 | ✅ | 选手真实姓名或昵称。 |
| **电话** | 文本 | ✅ | 选手的联系电话。 |
| **邮箱** | 文本 | ✅ | 报名时预留邮箱（预留给正式版登录校验使用）。 |
| **头像** | 文本 / 附件 | ✅ | **[Demo阶段注意]**：若后端采用本地直存，此处设为**文本**存图片 URL；若后端直接调飞书传附件，此处设为**附件**。默认使用 DiceBear API 生成专属默认头像。 |
| **角色** | 单选标签 | ✅ | 固定选项：`引航者` / `编织者` / `链接者` / `造物者` / `破壁者`。 |
| **自我介绍** | 长文本 | ❌ | 选手填写的个人简介。 |
| **所属团队** | **单向关联** | ❌ | 关联至【团队表】。若此字段为空，代表该选手当前处于"未组队"状态。 |
| **异常标记** | 文本 / 标签 | ❌ | 当选手点击"申请离队"后置此字段，用于管理员后台人工介入处理。 |

### 表 2：【团队表】 (Team Table)

**用途：** 记录队伍维度的信息、项目进度状态，并用于控制组队人数上限。

| 字段名称 | 飞书字段类型 | 必填 | 备注 / 业务规则 |
|---|---|---|---|
| **团队ID** | 自动编号 / 文本 | ✅ | 唯一标识符（如 `T-001`），系统生成或后端自动按规则写入。 |
| **队名** | 文本 | ❌ | 团队组建成功后，仅限**队长**填写 / 修改。 |
| **一句话宣言** | 文本 | ❌ | 团队展示标语，仅限**队长**填写 / 修改。 |
| **队长** | **单向关联** | ✅ | 关联至【用户表】的 `Builder号`。前端 / 后端校验权限的唯一依据。 |
| **当前人数** | 查找引用 / 聚合 | ✅ | 自动统计关联了该团队 ID 的用户数量。**当此值 >= 3 时，后端需拦截新增队员的请求。** |
| **受邀名单 (pendingInvites)** | 多选文本 | ❌ | 记录已发出但尚未被接受/拒绝的 Builder 号列表。系统以此计算"锁位"：`当前人数 + pendingInvites.length >= 3` 时，禁用队长发送邀请按钮。 |
| **队伍状态** | 单选标签 | ✅ | 选项：`头脑风暴中` / `开发中` / `Demo提交`。队长可在前端操作修改，默认值为"头脑风暴中"。 |

### 表 3：【系统控制台】 (System Config Table)

**用途：** 全局状态的控制面板。此表通常**仅维持 1 行数据**，前端通过轮询此表实现大屏与全员消息同步。

| 字段名称 | 飞书字段类型 | 必填 | 备注 / 业务规则 |
|---|---|---|---|
| **全局跑马灯通知** | 文本 | ❌ | 管理员在此手动输入文字。一旦有值，前端需在大屏和手机红条展示；清空则隐藏展示。 |
| **比赛结束时间** | 日期时间 | ✅ | 例如 `2026-05-20 17:00:00`。前端读取此时刻，用于在主页面自动计算并渲染倒计时组件。 |
| **强制解散触发** | 文本 | ❌ | **管理员工具：** 输入目标【团队ID】，后端轮询 / 侦测到后，清空该队所有成员的"所属团队"并删除此记录，实现一键踢人。 |

## 10. API 路径规范

所有前端请求统一走标准 RESTful 风格，中转后端在内部隐藏对飞书的调用细节。

### 10.1 统一响应格式

**所有 `/api/...` 路由必须返回标准 JSON 结构**，前端 Toast 提示统一依赖此格式：

- **成功响应**：`{ "ok": true, "data": { ... } }` — `data` 字段包含业务数据。
- **失败响应**：`{ "ok": false, "error": "错误信息说明" }` — `error` 字段为人类可读的中文错误描述，前端直接用于 Toast 展示。
- **例外**：`POST /api/auth/login` 成功时 Response Body 直接返回用户信息对象 `{ builderId, name, role, teamId }`（同时通过 `Set-Cookie` 写入 Cookie），不包裹在 `{ ok, data }` 结构中，以便前端一次性写入 Context。

### 10.2 路径列表

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/auth/login` | 登录校验，输入 Builder 号。成功后设置 HttpOnly Cookie 并返回完整用户信息（见 §3.1） |
| GET | `/api/user/me` | 获取当前用户完整信息 |
| GET | `/api/team/invites/received` | 获取当前用户收到的所有邀请列表 |
| POST | `/api/team/invite` | 发起邀请（Body: `{ targetBuilderId }`）。**若发起人未组队，后端自动创建新队伍并将发起人设为队长**；若发起人已是队长，则直接追加 pendingInvites |
| POST | `/api/team/invite/accept` | 被邀请方接受邀请（Body: `{ teamId }`） |
| POST | `/api/team/invite/reject` | 被邀请方拒绝邀请（Body: `{ teamId }`） |
| PUT | `/api/team/name` | 队长修改队名（Body: `{ teamId, name }`） |
| PUT | `/api/team/slogan` | 队长修改宣言（Body: `{ teamId, slogan }`） |
| PUT | `/api/team/status` | 队长切换队伍状态（Body: `{ teamId, status }`） |
| POST | `/api/team/leave-request` | 队员申请离队（打异常标记） |
| GET | `/api/system/status` | 大屏 / Dashboard 轮询全局状态（通知 + 倒计时） |
| GET | `/api/screen/teams` | 大屏获取全场队伍列表 |
| POST | `/api/upload/avatar` | 头像上传（Phase 1：本地直存；Phase 2：TOS） |

## 11. Demo 阶段数据流转模拟 (AI 编码约束)

### 场景 A：队长 A 邀请队员 B

1. **锁位校验**：后端查询【团队表】中 A 所在队伍的 `当前人数 + pendingInvites.length`，确认 `< 3`。
2. **发出邀请**：在【团队表】的 `pendingInvites` 数组中追加 B 的 Builder 号。
3. **返回结果**：向前端返回成功状态。

### 场景 B：B 同意加入甲队伍

1. **接受邀请**：后端将 B 的 `所属团队` 更新为甲队伍的 ID，将甲队伍 `pendingInvites` 中的 B 移除，将甲队伍 `当前人数 +1`。
2. **排他清理**：全局遍历所有其他团队的 `pendingInvites`，将 B 从中剔除（即使其他邀请失效）。
3. **返回结果**：向前端返回 B 已成功加入甲队伍。

### 场景 C：B 拒绝 / 忽略邀请

1. 后端仅需将甲队伍 `pendingInvites` 中的 B 移除，释放坑位，无需其他操作。

### 场景 D：队伍满 3 人（含 pending）

- `当前人数 + pendingInvites.length >= 3` 时，队长的邀请输入框和发送按钮立即置灰禁用。
- 任意 pending invite 被接受或移除后，重新校验是否可解除锁定。
